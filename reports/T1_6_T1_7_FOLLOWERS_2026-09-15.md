## Measured against the live provider (2026-09-15)

Read-only probes and one bounded A/B walk, Alchemy Robinhood, head 63,674,304:

| Probe | Result |
|---|---|
| One RPC round trip | ~0.46 s (`eth_chainId`, `eth_getBlockByNumber`, `StateView` calls alike) |
| `eth_getLogs` filtered by pool, recent range | 10k blocks → 1.1 s / 152 logs; 100k → 4.4 s / 1,144 logs; 500k → exceeds the 8 s browser request ceiling; 1M → provider 400 |
| `eth_getLogs` in dense history (block 20M) | 10k → 399 logs OK; 20k → 1,246 logs OK; 50k and 100k → over the response ceiling |
| Response ceiling | `MAX_RESPONSE_BYTES = 2 MB` in our own transport, not a provider limit |
| 100 block headers, sequential | 45.8 s |
| 100 block headers, batched 8 per envelope | 7.9 s (5.8x) |

The old cost model is therefore fully explained: ~5 round trips per 10k-block
chunk at 0.46 s each is ~2.0-2.2k blk/s, which is what both this run and the
other worker's independent 1,900 blk/s measurement produced. Chunk size and
round trips, not provider throughput, set the ETA.

## The process on arbitrary pools (2026-09-15)

Three pools created in the last 20,000 blocks (nobody selected them, they are not
in `selected_pools.py`) were driven through the whole process against the live
provider and the disposable local database:

| Pool | `find-anchor` | seed | register | walk | status |
|---|---|---|---|---|---|
| `0x2317a8c0…aab6` | found 63,719,020 (3.1 s) | cache | registered | 2 events, reconciled | `stored_history` |
| `0x4a6f7221…a885` | found 63,718,993 (4.9 s) | cache | registered | 2 events, reconciled | `stored_history` |
| `0xd2d5b6ad…46b2` | found 63,719,089 (4.7 s) | **refused** | registered | 2 ranges, reconciled | `stored_history` |

The third pool is the finding of this round: `seed` resolves the pool key through
the PositionManager's `poolKeys(bytes25)` cache, which only holds pools that
manager has seen, so a pool created another way is refused as `invalid_pool_key`
even though its own creation log proves the identity. `seed --anchor-block N`
now takes the key from that Initialize log (emitted by the configured
PoolManager, key hashing to the pool id) and the registration re-verifies it at
the canonical block, so the pool went from unservable to `stored_history` with
two live ranges.

What "any pool" still needs, in order:

1. **A trigger that survives an operator.** The read path runs as
   `domino_catalogue_reader` (SELECT only), so it cannot enqueue a request
   itself. Either the deployment grants a narrow requester role that may insert
   only into the queue table, or a read-path response variant tells the consumer
   to ask for the pool. Writing an operator CLI alone would not be persistent.
2. **A durable queue** (`pool_requests`: queued/registering/indexing/following/
   blocked) plus the worker that drains it, reusing the follower and the
   Initialize-log identity above.
3. **Serving before the walk finishes.** The range map cannot be reconstructed
   from on-chain state alone: `getTickInfo` gives a tick's net delta, not which
   lower/upper pair holds it, and the model's `ranges` are pair-keyed. So
   "exact since bootstrap" needs a decision: either serve the live 24 h window
   (state + a windowed log query, a new response variant for the frontend pin) or
   keep the walk as the only source of `ranges` and let the queue make it fast
   (6.3x here, times the pools walked in parallel).

## Invariants kept

- **No financial surface.** Both followers only read chain state and write their
  own public indexing tables; `managed_activity` still reports
  `executionAvailable: false`, and `IndexRpc` keeps signing and broadcast disabled.
- **The lag is the reorg window.** A follower never indexes past
  `head − lag`; reorgs inside that window are rewound by the indexer's own
  reconciliation, not committed as history.
- **Failures are visible.** Each target has its own consecutive-failure budget.
  One pool that cannot catch up stops the loop with the recorded reason instead
  of being retried in silence, and a failed round never advances a checkpoint.
- **A revision is a content version.** Coverage can advance over empty chunks
  without invalidating a paging client's revision; a chunk with an Initialize
  event still changes it.
- **Anchors are proven, never assumed.** Registration accepts an explicit
  Initialize block only when the decoded log at that block matches the pool id,
  block hash and complete key; `--find-anchor` decodes the log it finds and the
  registration verifies it again at the canonical block.
- **Capacity policy is unchanged.** `--capacity-profile` still selects the live
  range limit explicitly; the follower inherits whatever the operator selects.

## Operator commands

```bash
# T1.7: seed the six pools, then index and follow the catalogue.
backend/.venv/bin/python backend/manage_catalogue.py seed --selected
backend/.venv/bin/python backend/manage_catalogue.py index --start-block 58736592 \
  --through <head-200> --output reports/catalogue-backfill.json
backend/.venv/bin/python backend/manage_catalogue.py follow --lag 200 --max-passes 0 \
  --span-ceiling 100000 --max-seconds 86400 --output reports/catalogue-follow.json

# The alternative in the issue, instead of seeding: restart at the PoolManager origin.
backend/.venv/bin/python backend/manage_catalogue.py reset --start-block 9070 --confirm

# T1.6: confirm the six Initialize blocks, then register and follow.
backend/.venv/bin/python backend/manage_activity.py --find-anchor --selected \
  --search-from 9070 --search-span 10000 --search-max-spans 100
backend/.venv/bin/python backend/manage_activity.py --register --selected \
  --initialization-anchor <pool>=<block>
backend/.venv/bin/python backend/manage_activity.py --follow --selected --lag 100 \
  --span-ceiling 100000 --parallel-walks --max-passes 0 --max-seconds 86400 \
  --output reports/activity-follow.json
```

`--max-passes 0` means "until SIGTERM/SIGINT or `--max-seconds`" and is refused
without one of those, so a follower cannot be started unintentionally unbounded.
Both commands print one JSON line per round and exit non-zero when a bounded run
ended on failures.

`--span-ceiling` lets the follower grow its chunk towards the provider's useful
range and shrink automatically on `response_too_large`, `http_400`, a timeout or
the 2,000-log cap; `--span-floor` bounds the shrink. `--parallel-walks` switches
activity writers from the single global advisory lock to one key per pool, so
different pools can be walked at the same time. It is opt-in because the
cross-pool ledger writers (fees, positions, capital) still take the global
guard: with the flag on, they can observe a moving activity tail. Their own
checkpoints make that a retry rather than a corruption, but it deserves the
explicit flag until each of them is reviewed for the same fence.

## Not verified here, and what remains

- **No live chain run.** The six Initialize anchors still need the
  `--find-anchor` scan against Alchemy, and no backfill or follower has been
  started against the VM database. The commands above are the ones to run.
- **No service unit or egress rule.** These followers poll over HTTPS, so they
  belong to the existing reader-style egress rather than the WSS ingestor in
  T3.2. Until a permanent unit exists, run them with a transient unit, for
  example
  `systemd-run --unit=domino-catalogue-follower --uid=domino_catalogue_follower ...`,
  and add the unit plus its nftables scope as the follow-up.
- **The T1.7 decision is still open.** Both branches are implemented, but which
  one the operator takes (keep 58,736,592 and seed, or `reset --start-block 9070`)
  changes how much history exists afterwards. Seeding keeps the interval short
  and proves the six pools immediately; resetting re-derives every Initialize
  event at the cost of a 3.6M-block re-index.
- **Follower freshness is a lag choice, not a guarantee.** On a one-second chain
  the activity lag of 100 blocks keeps the read's 120 s freshness window with
  margin; a slower pass rate (large spans, provider limits) still shows up as a
  `stale` read, not as a silent zero.
- **`manage_activity.py` still autoregisters on the bounded index path.** That is
  the previous behaviour, kept for compatibility; the new `--register` path lets
  the six be registered in one explicit step without indexing.
