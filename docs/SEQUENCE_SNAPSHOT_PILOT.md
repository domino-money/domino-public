# Guided sequence read fallback — release gate

The owner screen may fail while Rabby performs roughly 48 sequential contract reads. This candidate adds one **read-only** `POST /api/read/v4/sequence-snapshot` from the Domino local RPC for `recent()` and `inspectRoot()` after Rabby rejects `eth_call` or `eth_getCode`. It does not change the deployed contracts, sequence policy, fees, publisher, operator, transaction construction or wallet signing.

The request contains exactly a lowercase owner address and an optional decimal NFT id. The server selects the fixed V1 deployment, selectors and `finalized` block; it checks the numeric block hash again before returning. Configuration must be version 4 with the local `rpc.domino.money` primary. By default, the snapshot uses that HTTPS primary. The private, V4-only `sequenceSnapshotLoopback: true` opt-in instead sends this snapshot through the fixed `http://127.0.0.1:18547/` endpoint of an independently qualified VM-local encrypted tunnel to the same node. The loopback transport disables proxies and redirects; it cannot select another address or fall back to public Robinhood or Alchemy RPCs. Other reads retain their existing routing. The Browser checks its connected account, chain 4663 and that block's hash through Rabby, then runs its existing ABI, bytecode, immutable-link, owner, pool and approval checks over the snapshot. The source-controlled factory and PositionManager pins remain required. A matching block hash **does not prove the state values** supplied by the local RPC: that RPC and the read service become a trust boundary. No arbitrary RPC method, address, calldata or URL enters this endpoint.

The new route is OFF by default at the gateway and Worker. If it is OFF or unavailable, one failed read leaves the original closed wallet error and stage on screen; the client does not replay the 48 wallet reads. A malformed snapshot fails closed. After a late Rabby read refusal, a single fallback gets at most 25 additional seconds within a 55-second total cap. There is no automatic retry of a wallet transaction. In particular, `create()` and its pre-send guard still run every verification through the wallet. This fallback may open the read form while approval or vault creation still fails under Rabby's read limit. A reliable, user-selected Robinhood Chain RPC in the wallet is an alternative to qualify for that write lane; the server never signs on its behalf.

## Qualify before enabling

1. Install the exact candidate source on a disposable Linux clone of the reader/gateway host. If using `sequenceSnapshotLoopback: true`, first establish and qualify the independently managed tunnel at `127.0.0.1:18547`; keep the flag absent or false until it is ready. Confirm its local RPC supports `finalized`, numeric historical state for that block, and the fixed deployment. Run the read-only probe from that checkout:

   ```sh
   backend/.venv/bin/python scripts/qualify-sequence-snapshot.py --owner 0x706627e3e75b0603c4b6f9a1ebbfc635da712747 --token-id 3136705
   ```

   Record the source commit, returned block/hash and elapsed time; the full request must finish under the gateway's 15-second upstream ceiling with the same result on repeat. No wallet keys or transaction are needed. Test this on the actual production-node configuration before touching the live listener; a synthetic test cannot establish its latency or finality behavior.

2. Test the whole read route OFF and ON in the isolated host: reader at loopback `127.0.0.1:8876`, gateway at loopback `127.0.0.1:8878`, Access service identity, and exact `POST /internal/read/v4/sequence-snapshot`. The gateway opt-in is `DOMINO_BRIDGE_V4_READS=sequence-snapshot` plus `--enable-v4`. Keep the existing v1–v3 settings. Verify owner/NFT input, origin, Access, unknown-path, size, timeout, reorganization and malformed response refusals. Use no real signer or production wallet private key.

3. After the source is integrated on `main`, CI is green, and the host runs the **same commit**, publish through `.github/workflows/read-path-release.yml` with `operation=publish`, that exact `source_sha`, `enable_sequence_snapshot=true`, and the existing `enable_public_data` setting. This opt-in extends only the production read tunnel to `/internal/read/v4/sequence-snapshot` and sets `READ_V4_BRIDGE_ENABLED=true`, `ENABLED_V4_READS=sequence-snapshot` on the read Worker. The ordinary release path leaves V4 OFF before its first activation, and later preserves its active state; v1–v3 routes stay intact. Do not enable the Worker before the host is qualified and serving the matching route.

4. Confirm the public same-origin route returns the versioned 1.0.0-rc.1 contract for the owner/NFT, then press **Read my sequences** on the site with Rabby connected to the owner account. Inspect the returned root and predicted vault. Keep all transaction approvals and confirmations under the owner's manual control. If preparing approval/creation still fails, capture only the closed stage and qualify the wallet RPC separately; do not turn on the automation service to compensate.

Rollback uses the reviewed `.github/workflows/read-path-release.yml` dispatch with `operation=disable-sequence-snapshot` and `source_sha` set to the exact deployed `main` commit. That operation first sets `READ_V4_BRIDGE_ENABLED=false` on the read Worker, then removes only the V4 path from the production tunnel; it retains the V1–V3 flags and paths. `enable_sequence_snapshot=false` on an ordinary publish **preserves** an already enabled V4 route and is not rollback. Afterwards, remove `DOMINO_BRIDGE_V4_READS=sequence-snapshot` and `--enable-v4` from the host's reader/gateway launch configuration and restart those services; verify the public route is 404 and the V1–V3 routes still answer. The app then preserves the original wallet-read refusal. This route cannot create, approve, resume, collect, swap or reinvest anything.
