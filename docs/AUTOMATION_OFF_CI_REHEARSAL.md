# Synthetic Ubuntu check for the automation OFF boundary

The manual [Automation OFF synthetic rehearsal](../.github/workflows/automation-off-rehearsal.yml) workflow runs on a disposable GitHub-hosted Ubuntu 24.04 runner. It has no repository secrets, database, RPC endpoint, signing key or mainnet transaction path. It does not install or start an automation service.

The first step builds a plain `git archive` at the checked-out full commit, hashes it, and requires the installer's CLI plan to match the same archive in-process. It confirms the five exact unit texts have no `[Install]` section, all three private configuration gates are present, and the plan says services, configuration and keys remain absent. The second step uses `systemd-analyze verify` on those unit texts in a temporary directory and a synthetic PostgreSQL dependency. It creates disposable OS users and a Unix socket owned by `domino-gas-reservation`, then proves the real Linux `SO_PEERCRED` and socket mode with synthetic replies: automation and signer may reserve; settlement may attest but cannot reserve; automation cannot attest; an outsider cannot connect. Only the expected three operations reach the synthetic service.

Once this workflow file has landed on the default branch, invoke it manually against that exact integrated commit. GitHub does not offer a newly added `workflow_dispatch` file from an unmerged PR, so the native runner check is post-merge evidence; the local `plan` check and regular PR CI are the pre-merge gates. A successful result reports `nativeInstallerApplied: false`, `servicesStarted: false`, `rpcCalls: 0` and `mainnetTransactionsSent: false`. Those fields are deliberate limits of the evidence, not a substitute for an install receipt.

The actual `install_automation.py --inspect` and `--apply` still require a separate, isolated Ubuntu clone with the exact root-owned Python 3.14 lock, PostgreSQL 16 socket and peer foundation, already receipted financial upgrade, protected systemd lanes and fork-only RPC. The generic GitHub runner has none of that foundation, and the repository contains no complete disposable host provisioner. Run the [host rehearsal plan](AUTOMATION_INSTALL.md) on a clone before treating the native installer or settlement pass as qualified. The active VM must not be used for this synthetic check.
