# Position and wallet activity

Updated 7 October 2026. The integrated V2 build presents one wallet activity list, a four-row overview and paginated full history. Position Activity uses the same public history, with chain/DEX/position identity checks. Existing fee settlements remain visible; when exactly one matching financial operation names the position and transaction, its fee settlements appear inside that receipt. Different operations in one transaction are not discarded.

Public `read-v6` activity and private `execution-v1` evidence remain separate sources. Only the authenticated execution controller reads private records, with its existing session/CSRF, owner isolation, cache rules and 30-second read floor. Connecting a wallet does not sign in. Unsigned cancelled intents are internal records in a collapsed disclosure, not transactions or part of the four-row summary.

The wallet-keyed public pager retains cursor, token metadata and loaded pages across navigation and transient failures. It honours Retry-After, pauses while hidden and bridges a refreshed head back to the loaded history. A page with no visible matches still permits continuation. Unfinalized rows can be replaced only within a reread window of a current chain whose indexed snapshot covers them; unavailable/behind chains cannot erase their loaded history.

## Existing contract boundaries

- `execution-v1` lists by `intentId`, not time. It supplies no created/updated/cancelled timestamp and no direct position/vault/mode reference. Its initial five pages are not guaranteed to contain the latest five pages chronologically. The frontend keeps further pagination and labels unavailable dates; it does not estimate time from block numbers or when the browser received a reply.
- A confirmed private receipt can inherit a timestamp only when an existing validated public record has the same chain, block number **and block hash**. Otherwise its date is unavailable. The legacy generic chain client is not used: the current fixed Domino read routes do not expose arbitrary block headers, and public RPC/provider reads are prohibited by the repository's RPC policy.
- A complete chronologically paged private feed requires a compatible producer contract with temporal cursor and safe operation identity/date fields. `intents.created_at` and `journal.created_at/updated_at` exist but are not exposed to this reader. Unsigned cancellations currently store only state, so their historical cancellation time cannot be reconstructed from those fields. New exact cancellation timestamps require recording that event; old unknown dates must remain unknown.
- Public activity has no overall 20/50-record cap; 20 is the page size. It covers indexed Domino events, not every wallet transaction or every off-chain attempt. A failed V2 transaction without indexed events is not manufactured from the absence of a receipt.
- Portfolio is bounded and has no cursor: 50 automation containers, 100 positions, 100 mandates, 50 credits and 300 token metadata entries. Only the first three have `truncated` flags. Public activity paging is independent. Historical creation/registration records also establish position associations; incomplete context is disclosed. Complete position attribution and token-pair context beyond these bounds require receipt enrichment or a compatible point lookup/paginated context API.
- Do not attribute a wallet-wide nonce cancellation to a particular position without evidence. Do not deduplicate a transaction hash alone: several valid operations can share it. Do not move private intents into the public read endpoint.

Focused tests: `app/tests/v2/activity-history.test.mjs` covers paging, refresh gaps, errors/backoff, scope, metadata, reorg coverage and identity. `app/tests/v2in-browser/lists.test.mjs` covers the single overview limit, explicit sign-in, unknown dates, unsigned cancellation detail, older-page recovery, wallet changes and position paging beyond unrelated events.
